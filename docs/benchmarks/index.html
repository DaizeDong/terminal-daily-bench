benchmarks

The benchmark is not a fixed set. Each day the pipeline mines merged pull requests, rebuilds their environments and seals a suite named after that date. A suite is live while it is fresh — the gold patch and protected tests stay withheld and scoring happens server-side — then it is archived and released in full so anyone can reproduce it.

how a daily suite lives

mined → built → sealed → archived
step 1

mined

The day's candidate pull requests are pulled from public repositories after they merged, so no released model can have trained on the fix. Freshness is certified per task.

source: real merged PRs
step 2

built

Each candidate is rebuilt into a container at the parent commit. A task is kept only if its fail-to-pass tests actually fail before the fix and pass after it.

oracle must reach reward 1.0
step 3

sealed — live

The suite is frozen. Gold patch and protected test bodies are withheld; only the failing test IDs are published. Submissions are scored server-side by re-laying the protected tests.

withheld for two weeks
step 4

archived

After two weeks the suite is released whole — environment, protected tests and the reference solution — so results can be reproduced locally with tdb run.

released in full
invariant

the gate never changes

Live or archived, a solve is minted the same way: apply the patch, throw the workspace tests away, re-lay the protected tests from the trusted package, run them with the network cut.

what a suite guarantees

Every published number on a suite page comes from that gate. A claimed reward is advisory only — it is replayed on ingest before it can appear anywhere.

the two-week window

live → archive, on a date, not on a decision the full task format →

The split is mechanical. tasks/publish_tasks.py sets ARCHIVE_WEEKS = 2 and publishes a task as archive when (today − merge_date).days ≥ 14, otherwise as live. Nobody decides per task; the merge date of the upstream pull request does. That is why a suite's status can be read off its own name.

what a live task holds back

The protected assertion bodies, the test patch and the reference solution. What you do get is the environment, the runner and FAILING_TESTS.json — the failing-test IDs and nothing else. Enough to attempt the task, not enough to read the answer.

FAILING_TESTS.json · failing_test_ids only
why

the reason it is withheld

Publishing the gold patch on day one hands a future training run the fix, and publishing the assertion bodies invites a patch written against the assertions rather than the bug. Holding both back for the window blocks memorization and test-fitting while the suite is being scored.

what the archive owes you

After the window the same suite ships whole — protected tests, test patch and reference solution — so any published number on it can be re-derived locally, including the oracle baseline. The withholding buys freshness; it does not buy permanent opacity.

tdb run · tdb oracle

The contract cuts both ways: while a suite is live we score it and you cannot; once it is archived you can reproduce every cell of it and we no longer have anything you do not. Nothing about the gate differs between the two — the same protected tests are re-laid either way, so an archived re-run and our live score are the same measurement.
