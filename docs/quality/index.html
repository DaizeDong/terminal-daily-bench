msq · multi-angle selection-quality

we measure the benchmark, not just the models

A solve-rate column tells you who scored higher. It never tells you whether the task set can separate models at all. This page is the instrument for that missing axis: it reads the gate-scored (task × model) matrix and reports, separately, how well today's set discriminates — plus how far it is from supporting a research-grade claim.

full methods the leaderboard it grades

MSQ is a pure function over plain lists. It reads no reward gate and gates no accept, so false_accept = 0 cannot be perturbed by anything on this page. Every randomized routine is seeded, so a re-run reproduces the interval.

Standard error scales as 1/√N, so the bootstrap SE at today's N extrapolates to the task count that would buy a research-grade interval. This is the number the daily pipeline is aimed at — it is a target, not a promise.

what each axis means

one sentence each
axiswhat it asksreads
D Discriminative yield: the fraction of tasks that split the field (0 < solvers < n_models) — a task everyone or no one solves carries zero information about who is better. [0,1]
C Difficulty coverage: the normalized entropy of per-task solve-rate buckets — 1 when the set spans easy to hard, 0 when every task sits at the same difficulty. [0,1]
M Monotonicity: the fraction of tasks with no strong ability inversion — a weaker model passing a task an abler one misses is a noise, mislabel or gameability signal. [0,1]
IRT 2PL Fisher test-information: each task is fit an a (discrimination, from its point-biserial correlation) and b (difficulty, from its solve-rate); information is additive, and SE = 1/√I. ≥ 0
KR-20 Internal-consistency reliability for binary items: do the tasks measure one coherent latent ability, or noise? It can go negative when items contradict each other. ≤ 1
D CI A bootstrap over resampled task rows (seeded, 95% central interval) — the honest width of D at the current task count. [0,1]

Two further axes ship in the library but are not on this card because they read task signatures and ordinal gate-states rather than the solve matrix: A angle coverage (build → partial → full-F2P → clean, each conditioned on reaching the previous stage) and R diversity (1 − the near-duplicate rate over {repo, files, f2p} signatures). Both are advisory. See the methods note.

why we do not claim more than this

the honest part

The readiness verdict on this page is almost always not yet, and we publish it anyway. Here is what a small-N day genuinely cannot support:

  • A ranking is not a result. At a handful of tasks per model, the Wilson interval on any single model's rate covers most of the other models. The order on the leaderboard is a reading of one day, not a finding.
  • D at small N is coarse and jumpy. With few tasks, D can only take a few discrete values, and one task flipping moves it by a large step — which is exactly why the bootstrap interval is so wide.
  • KR-20 below the bar means the set is not yet one instrument. Under the conventional 0.70 rule of thumb, the items are not yet demonstrably measuring a single coherent ability; treating the total score as a skill estimate would be overreach.
  • Vacuous highs are not achievements. M is 1.0 whenever there is no ability separation left to violate, so a perfect M on a thin day is the absence of evidence against the set, not evidence for it. We show the raw value rather than hiding it behind a composite.
  • The required-N figure is an extrapolation. It assumes the next tasks are drawn like today's, and it comes from a bootstrap SE that is itself noisy at this size. Read it as an order of magnitude.

What the card is good for: catching a day whose set has quietly collapsed — every task all-pass or all-fail, an item correlating negatively with total score, a difficulty band entirely missing — before anyone reports a leaderboard from it. That is a defect detector with an explicit threshold, and it runs every day.

Readiness is advisory only. It never gates an accept, never touches the reward path, and cannot promote or demote a task.

run the card yourself

# results.jsonl — one record per (model, task) run, exactly as `tdb run` emits
# {"task":"td-1","model":"A","reward":1.0}

tdb quality results.jsonl

It builds the (task × model) matrix (records with model == "oracle" are excluded), prints the axes and the readiness line, then emits the full machine-readable card as JSON. It requires at least 1 task and 2 models — multi-angle quality is undefined with a single model column — and exits 2 otherwise.
