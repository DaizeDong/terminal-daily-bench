Recording a submission

The recorder writes a pending row; nothing it does can write a score.

The recording CLI

web/submit_result.py reads a submission JSON from stdin, in the shape the schema fixes.

Validation rules

All eight of date, submitter, model, model_build, scaffold, harness_version, task and patch must be present and non-empty; patch must be a unified-diff string and task must start with td-. reward_claimed is advisory only: it is validated against nothing, and it never becomes a score. Receipt signatures come only from the official signer, and the authenticated submitter comes from the deployment auth layer, never the JSON body.

One immutable cell per submission

record computes a full SHA-256 content id over patch, authenticated submitter, model build, harness version and task, which yields one immutable authenticated cell per suite/build/harness/task. Partial, duplicate and cross-date sets are left unranked, and every rebuild re-verifies the receipt signature and content binding.
