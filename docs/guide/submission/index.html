Submitting to terminal-daily-bench

A scaffold produces a candidate patch; the execution gate is the sole reward authority.

How scoring works

The reward comes from Harbor’s result.json, read by harbor_score._read_harbor_reward — the same reader the private admission gate uses. Harbor applies the patch inside the task container, re-lays the protected tests/ and runs them under a network cut, which is why scoring requires an apptainer/singularity host. No external service or hidden API is required to score a patch.

Why a patch cannot cheat the score

The protected tests/ are re-laid by Harbor from the trusted task package after the patch is applied, so a patch that edits tests/ only changes an agent-side workspace that is discarded before scoring. Runtime egress is cut — --network=none, or the offline --ek switch injected by harbor_score._maybe_inject_offline_eks. The reward is byte-for-byte execution truth from result.json, not any string the model emitted: the model is the subject under test; it is never the judge.

Recording is not replay

web/submit_result.py records the patch; it does not score it. The stored entry carries verify_status="pending", verified_reward=null and no false_accept value, because only an execution-gate receipt can set a verified reward. A claimed reward is never trusted: only an official protected-test replay receipt can enter the verified ranking.

Submission schema

JSONL, one line per (model, task) cell; every key except reward_claimed is required, and the validation rules and the recording CLI have their own page.

Operator-only replay authority

Receipt signing and verification are operator-only, and they use Python cryptography’s in-process Ed25519 primitives: web/receipt_auth.py does not search PATH and does not invoke an external OpenSSL process. A missing or invalid replay extra fails closed before signing or acceptance, and what the worker has to prove before it may sign is on replay integrity.

Community submissions

The public bundle does not run a replay worker, so pending rows remain in community_pending, a separate audit view excluded from ranking; a row enters community_verified only with an Ed25519-signed v2 receipt bound to the frozen suite, runner, Harbor, runtime image, enforced offline canary and pinned authority key, and ranking also requires the complete frozen roster.
