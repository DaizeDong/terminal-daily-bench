quickstart

terminal-daily-bench is a living, execution-graded coding-agent benchmark.

The reward is the test outcome, never a model’s opinion.

That covers claim bypass only; semantic verifier false-accept remains unmeasured.

How a run is scored

  • The model sees the task instruction and produces a patch.
  • Harbor re-lays a protected test suite the model never sees.
  • The suite runs under a network cut; the reward is its outcome.

Requirements

ComponentNeeded byNote
Python ≥ 3.11 everything the scoring core is pure stdlib; there are no runtime dependencies
apptainer/singularity host tdb run, tdb oracle both invoke harbor run ... -e singularity, which executes each task’s SIF image
OpenAI-compatible endpoint tdb run with a real model tdb oracle needs no model
— tdb quality needs neither harbor nor a model
Current availability: our scored runs use a private, locally patched Harbor 0.13.1 fork. Stock upstream Harbor rejects this bundle’s singularity backend options, so a third party cannot currently run tdb run or tdb oracle end to end. The task packages, tdb doctor, tdb quality and tdb publish remain usable without that fork. No publication date is promised.

Install

With uv

uv tool install terminal-daily-bench

From a checkout of the release bundle

pip install -e .

Verify

Both install the tdb console script (terminal_daily_bench.cli:main in pyproject.toml).

tdb --version          # -> terminal-daily-bench 0.1.0

Configure the model endpoint

The model call goes to a generic OpenAI-compatible endpoint: OpenAI, OpenRouter, vLLM, LiteLLM, or a local server.

export OPENAI_BASE_URL=https://api.openai.com/v1   # any OpenAI-compatible endpoint
export OPENAI_API_KEY=sk-...                        # bearer key, read from env, never stored
VariableDefaultNote
OPENAI_BASE_URL https://api.openai.com/v1 requests go to <base>/chat/completions
OPENAI_API_KEY none bearer key, read from env, never stored

Reasoning-model fallback

If the upstream rejects max_tokens, the client automatically retries with max_completion_tokens.

Run tdb doctor first

tdb doctor tasks/archive/td-fc90ea8b76d5f6b6

It reports which of the pieces below your host is missing, before you spend a model call finding out.

Build the task image

A published task ships no image: docker_image is the portable string environment/Dockerfile.

The producer’s host-specific .sif path is stripped on publish, so nothing executes that as-is.

Build the task’s own Dockerfile once, then point docker_image at the result.

IMG=$(scripts/build_task_image.sh tasks/archive/td-fc90ea8b76d5f6b6)
sed -i "s|^docker_image .*|docker_image = \"$IMG\"|" \
    tasks/archive/td-fc90ea8b76d5f6b6/task.toml

Score a model on a task

tdb run <MODEL> tasks/archive/td-fc90ea8b76d5f6b6

<MODEL> is any model id your endpoint accepts, e.g. gpt-4o-mini.

What single_shot_patch does

  • Shows the model the task instruction plus the source file(s) the reference solution touches.
  • Asks for a git apply-ready unified diff.
  • Applies that diff inside the task container.
  • Harbor re-lays the protected tests/, and the reward is written to result.json.

Where the record goes

tdb run gpt-4o-mini tasks/archive/td-fc90ea8b76d5f6b6 --out results/gpt4o-mini.json

Run the oracle baseline

The oracle model id runs the task’s real solution/oracle.patch; no model is called.

tdb oracle tasks/archive/td-fc90ea8b76d5f6b6

It proves the execution gate returns reward 1.0 on a correct patch.

Run it before spending model calls

If oracle does not yield reward = 1.0, the environment, not the model, is the problem.

Only archived tasks (≥ 2 weeks old) ship solution/. Live tasks withhold the gold patch and the protected test bodies; submitted patches stay unranked until official replay. Archive vs. live · tasks/SCHEMA.md.

The result record

Each run writes one JSON record. A solved run looks like:

{
  "model": "gpt-4o-mini",
  "task": "td-fc90ea8b76d5f6b6",
  "task_dir": "/abs/path/tasks/archive/td-fc90ea8b76d5f6b6",
  "scaffold": "single_shot_patch",
  "reward": 1.0,
  "solved": true,
  "patch_applied": true,
  "error": null,
  "model_endpoint": "https://api.openai.com/v1/chat/completions",
  "runtime_sec": 142.7,
  "false_accept_check": {
    "gate": "harbor_protected_tests",
    "reward_source": "result.json via harbor_score.read_harbor_reward",
    "protected_tests_relaid_by_harbor": true,
    "model_is_judge": false,
    "model_patch_touched_tests": false,
    "scope": "protected_test_replay_integrity",
    "claim_acceptance_without_replay": false,
    "semantic_false_accept": null,
    "false_accept": 0
  }
}

Fields

FieldMeaning
scaffold single_shot_patch for a model run, oracle_baseline for tdb oracle
reward the protected-test outcome
solved reward >= 0.999
patch_applied true once a reward is parsed, false if the patch failed to apply, null if the gate never reached the apply step

Failure never scores

  • Runs are BAD-safe: any failure yields reward = 0.0 / solved = false, with the cause in error.
  • Covered: no diff, patch does not apply, hung trial, unparseable result.
  • Never a positive score on a crash.

The false_accept_check block

This block records which deterministic execution boundary produced the score.

It does not by itself establish semantic verifier quality.

FieldMeaning
gate: "harbor_protected_tests" scoring is the harbor execution gate and nothing else
reward_source the reward is read from result.json with the same reader the admission gate uses (harbor_score.read_harbor_reward)
protected_tests_relaid_by_harbor: true the trusted tests/ are re-laid from the task package after the patch, so a patch that edits tests only changes a discarded workspace
model_is_judge: false the model is the subject under test, never the judge
model_patch_touched_tests flags whether the model’s diff touched any test-named path (informational; it cannot affect the score)
false_accept: 0 a compatibility field scoped by scope to replay integrity; it means no acceptance bypassed the protected test run

false_accept: 0 does not estimate semantic verifier false-accept, which remains null pending an exploit corpus.

Aggregate a quality card

Collect result records into one file — JSON Lines (one record per line), or a JSON array.

cat results/*.json | jq -c . > results.jsonl
tdb quality results.jsonl

Input requirements

  • tdb quality builds a (task × model) solved matrix.
  • It needs ≥ 1 task and ≥ 2 models.
  • Records with model: "oracle" are excluded from the matrix.

Example output

tasks=40 models=6
  D(discrimination)=0.517  C(coverage)=0.750  M(monotonicity)=0.912
  IRT test-information=8.431  KR-20 reliability=0.78
  D 95% CI=[0.402, 0.631]
  readiness: NOT-ready (bottleneck=discrimination, need ~64 tasks)

The final line of stdout is the full card as JSON (msq, irt, reliability, readiness) for machine consumption.

Submitting results

  • Every submission is recorded as pending and its claimed reward is ignored.
  • The public bundle does not run a replay worker.
  • Only an operator-published gate receipt can enter the verified ranking.

See submission and ../CONTRIBUTING.md.
