How a task gets its labels

The rules that put a capability code on a task, and what the coverage report built from them does and does not claim.

What triggers a label

The two unconditional rules are why C5 and C4 sit on nearly every archive package.

A changed path matches a path rule
Tags that rule’s code, once per matching path.
A token rule matches the diff
Tags that rule’s code. Added lines only, word-boundary matched — a deleted line or a diff header never tags a task.
The test diff is non-empty
Always adds C5; the test diff is what carries the verifiable signal.
A changed non-test source file
Always adds C4.
Nothing matched
Defaults to C3. The label list is never empty.
Order
Hit count descending, then code number. The list is a total order, not a set.

A label set is not a scoreable axis

Per-axis coverage and gate status on today’s catalogue is on the capability coverage report; a defined label set is not a scoreable axis, and that page says which axes clear the gate. The codes themselves are declared in the taxonomy.

Reading the capability coverage report

Every axis is listed
All fourteen axes are listed. An axis this catalogue does not cover is a fact about the catalogue, not a row to hide — so an axis carrying no task at all is listed at zero rather than dropped: a missing row reads as an axis that does not exist, which is a different claim from an axis this catalogue never reached.
The co-occurrence grid
One column per re-derivable package, one row per axis; a mark is presence, never a degree. No model outcome is in that figure — it is not a solve result. Columns are ordered by how many labels a package carries, so the dense left edge is arrangement, not a finding.
Multi-valued labels
A task carries every code its diff triggers, so the per-code counts do not sum to the task count.
The unmeasured criterion
min_admitted_subtests counts the subtests surviving a unit-test-validity audit, and no such audit has classified this catalogue. Unmeasured is not failed, and it is certainly not passed — so no axis clears the publish gate whatever its counts say.
The audit on record
The unit-test-validity audit on record does not describe this catalogue (release b3fc3e6, experiments/reports/unit-test-validity-r001/SUMMARY.json). It measured a different corpus at a different release commit; its per-axis counts describe that corpus, so they are not reproduced on the report and min_admitted_subtests stays unmeasured here.
Packages that cannot be tagged
The tagger reads the oracle diff and live withholds it, so a live package’s task.toml keywords stand as declared, never re-derived — and every count on the report is over the packages that could be checked.
