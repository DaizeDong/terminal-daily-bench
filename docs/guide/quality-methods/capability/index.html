The capability taxonomy

Where C1–C14 are declared, and what the fourteen codes are.

The capability taxonomy (C1–C14)

Correction. An earlier revision of this page deleted the C1–C14 claim, on the grounds that nothing defined the codes. That was wrong, and it is restored here rather than re-added silently: the codes are defined in one place and the assignment is deterministic.

Source of truth
CAPABILITY_TAXONOMY in td_pipeline/selection.py; code, name, scope and tagging rules are declared once, per code.
Tagger
label_capabilities(candidate) — static path rules and patch-token rules. No model, no heuristic scoring, no human pass.
Inputs
Three, all from the package: the changed-file list, the oracle diff, the test diff. The task.toml prose is not read.
Determinism
Same inputs, same labels. Re-running the tagger reproduces each package’s shipped capability_labels exactly.
Multi-label
A task carries every code its diff triggers, not one. The counts per code do not sum to the task count.
Live packages
Not taggable. Live withholds solution/oracle.patch, so the tagger has no oracle diff to read.
In the registry
A capability chip selects both kinds of evidence — re-derived and declared-only. The Capability column is what says which kind a given row has.
Not a difficulty
A label says what the fix touches. It never says how hard the task is.
