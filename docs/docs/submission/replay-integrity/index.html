How submissions are checked

Operator evaluation connects a submitted patch to a reproducible test outcome.

Use consistent conditions

Operators evaluate a submission against a specified task set and evaluation environment. A result must identify those conditions before it can support a comparison.

Check the task environment

The evaluator checks that the task image and runtime match the required environment. Unexpected changes stop verification rather than producing an accepted score.

Check the evaluator

The task runner is checked before and after execution so a result cannot silently come from a different evaluator.

Read the actual result

The published outcome must come from the protected test run for the submitted patch. A replacement result file or a contributor’s claimed score is insufficient.

Verify network restrictions

For offline tasks, operators check that the environment can reach the network normally and cannot reach it during isolated evaluation. An inconclusive check is an infrastructure problem, not a failed task.

Separate checking from publication

The systems that evaluate results and publish accepted results have separate permissions. Contributors cannot approve their own submissions.

Current limits

The public release does not provide an operational verification service. Production verification remains pending until operators demonstrate the required execution, isolation, and deployment checks in the real environment.

Tests of the verification code alone do not demonstrate that deployment. Protected tests may also miss incorrect solutions; that error rate remains unmeasured.
